## 0. Назначение и три принципа

Регламент определяет, как оформлять прогоны (батареи, линзы, пробы), какие артефакты куда класть, как они подписываются в реестр и как публикуются. Процедура одинакова для любой среды исполнения.

1. **Offline-first.** Каждый шаг проверяем без сети. Сеть нужна только: pull/push, пост во внешний тред, доступ к SUT, если прогон живой.
2. **Repo-relative.** Никаких абсолютных путей в скриптах, метаданных и артефактах.
3. **Полный хеш в данных.** В данных, индексах и сравнениях кода — только полные SHA-256 (64 hex). Короткие формы (16 hex + `...`) допустимы только в человеческих текстах. Известный дефект: `build-index.mjs` записывает `chain_head` в INDEX.json урезанным до 16 hex — патч планируется после текущего пуша; до него сверку пинов вести по полным хешам записей (`prev_record_hash` в записях полные).

### 1.2. Платформа прогона (вместо фиксированного «стенд-репо»)

Единого стенд-репозитория **не существует и не должно существовать**. Стенд поднимается под прогон, консоль и CI — аналоги на других машинах. Три вида платформы:

| Вид | Что это | Особенности |
|---|---|---|
| `sandbox-stand` | Двигатель + сценарии + demo-SUT (`demo-sut/`, `demo-buyer/`, `engine/`) поднимаются в песочнице на время прогона | Самая воспроизводимая; состав собирается под задачу |
| `console` | Консоль (`argus-console`): двигатель и сценарии в консервированном виде | Стабильнее, но тоже меняется — не догма |
| `ci-action` | Action (`argus-action`): та же матрица у клиента | Машина клиента; состав фиксируется workflow'ом |

**Правило платформы:** система и протоколы меняются, сценарии меняются под них — поэтому состав платформы фиксируется **на каждый прогон** в пре-регистрации (версия/дайджест двигателя, набор сценариев, цель SUT) и повторяется в `run.json` (раздел 3.3). Изменение сценариев или протокола = новая пре-регистрация, а не правка старой.

## 2. Жизненный цикл записи (P0–P6)

| Фаза | Что делается | Гейт (что должно существовать) |
|---|---|---|
| **P0. Постановка** | Что тестируем; тип записи (`seal` / `finding` / `correction`); вопросы к сторонам — **до** фроза | `tools/registry/drafts/NNNN-<slug>.<type>.draft.json` |
| **P1. Пре-регистрация** | Строки матрицы (id, сценарий, предусловия, ожидаемое, **row unit**, pass-правило), boundary-декларации, пины (SUT, сценарии, двигатель). Фроз до первого артефакта прогона | Draft с заполненными пинами, закоммичен до прогона |
| **P2. Платформа** | Поднять/выбрать платформу (1.2), зафиксировать состав в run.json; чистое дерево, SUT на пине | Каталог прогона с run.json |
| **P3. Прогон** | Скрипты пишут только в свежий каталог прогона; сырые выходы без правок; нормализованные строки + дайджесты клеймов | `raw/`, строки, claims |
| **P4. Верификация** | Пересчёт всех пинов; `node tools/registry/verify-registry.mjs` (и `--registry=agent`, если писали в агентскую цепь); сборка manifest | manifest + зелёный verify |
| **P5. Подпись** | Строгий порядок N→N+1→N+2; pre-sign чек-лист (раздел 5.3); `sign-record.mjs` или `offline-sign.mjs`; verify после каждой | Записи в `attestations/records/`, INDEX пересобран |
| **P6. Публикация** | Push → CI регенерирует каталог сайта (`latest-seal.yml`) → пост во внешний тред (head, счётчики, пины) | Push + пост |

**Правило фроза.** Строки замораживаются как опубликованы; после прогона ничего не переинтерпретируется. Позднейшие уточнения — `correction` (через `amends`) или `ERRATA.md` для текстовых описок; запечатанная запись никогда не переписывается.

**Правило повторного прогона.** Один прогон = один каталог с UTC-штампом; повтор — новый каталог; канонический фиксируется записью.

## 3. Форматы файлов и именование

### 3.1. Общие правила

- Записи: `attestations/records/NNNN-<slug>.<type>.json`; NNNN — сквозная глобальная последовательность (номер записи — универсальный хэндл).
- Types: `seal` (прогон был: SUT на коммите X, сценарии S на запиненных версиях, вердикты валидны, **полный список findings приложен**), `finding` (дефект в стороннем компоненте, раскрыт в названном месте, живой статус), `correction` (пост-коррекция через `amends`). Отдельная цепь: `self-test` (агентские самопроверки).
- Время: UTC, ISO-8601 с суффиксом Z (`2026-11-22T08:00:39Z`). Кодировка UTF-8, LF, без BOM. Никаких секретов и приватных ключей в артефактах.
- `INDEX.md` / `INDEX.json` — только генерация `build-index.mjs`, руками не правится никогда.

### 3.2. Draft-запись (P0–P1)

Draft не содержит `seq`, `record_id`, `prev_record_hash`, `signature` — их назначает подписант. Ключевые поля целевой записи: `type`, `title`, `subject` (repo/component/commit), `run_ts`, `scenarios`, `evidence` (записи kind `file` пинуют SHA-256 артефактов — правка артефакта ломает seal), `findings_summary`, `notes`, `self_run`.

### 3.3. run.json (каталог прогона)

```json
{
  "record_id": "NNNN",
  "prereg": { "id": "NNNN-<slug>.<type>.draft.json", "sha256": "<64 hex>" },
  "platform": {
    "kind": "sandbox-stand | console | ci-action",
    "engine": { "name": "<argus engine | argus-console>", "version_or_digest": "<версия или sha256>" },
    "scenarios": { "source": "<SCENARIO-REGISTRY + файл сценариев>", "digest": "<64 hex>" },
    "sut": { "target": "<цель>", "commit_or_version": "<пин>" }
  },
  "host": { "class": "sandbox | external-coder | operator-local | client-machine", "os": "…", "runtime": { "node": "…", "python": "…" }, "tz": "UTC" },
  "window": { "start_utc": "<ISO Z>", "end_utc": "<ISO Z>" },
  "runs": [ { "argv": "<repo-relative команда>", "exit": 0, "log": "raw/<имя>" } ]
}
```

### 3.4. Evidence pack

Фактический layout (см. `attestations/evidence/0018-boundra-a10/`):

```
attestations/evidence/NNNN-slug/
├── README.md            # что это, как читать
├── manifest.sha256      # sha256 всех артефактов пака
├── export-hashes.json   # дайджесты экспортов/клеймов
└── runs/
    ├── <имя>.jsonl              # основной лог строк матрицы
    ├── <имя>.jsonl.summary      # сводка
    ├── <имя>.adapter.jsonl      # адаптер/транспорт
    ├── <имя>.stand.json         # состав платформы прогона
    └── <имя>.state/             # состояние (audit.jsonl, spend.db и пр.), когда есть
```

**Правило неизменяемости:** после пина в записи файлы пака не правятся; ошибка = новый артефакт + `correction`/note.

### 3.5. Строки матрицы

- `unit` объявляется в пре-регистрации: `attempt` или `verdict`. Вердикт-строки не несут per-attempt кортеж; нужны попытки — unit = attempt.
- Для линзовых записей (классификация по записям): готовая классификация в evidence **не кладётся** — чекер выводит её сам из result-дайджестов между попытками одного платежа; в строках — входы для пересчёта (кортеж попытки + result binding, обе попытки, включая отклонённую).
- Несортируемое — вердикт `absent`: это честный результат, не сбой.

## 4. Реестр: цепи и ключи

### 4.1. Цепи

- **Main** (`attestations/records/`, INDEX в корне `attestations/`) — операторские записи, подписанные ключом из allowlist.
- **Agent** (`attestations/agent/`) — самопроверки автономных сессий: per-session ключи, namespace `argus-agent-self-<seq>`, тип `self-test`; каждая запись пинует `main_head_at_issuance` (порядок, устойчивый к подмене, относительно main-цепи без слияния цепей); анти-флуд гейты: блок spend и ≥1 evidence-запись типа `file` обязательны. Никогда не мержится в main и не оператор-ваучируется.

### 4.2. Криптография и доверие

- Подпись: **Ed25519 над canonical JSON** (отсортированные ключи, без пробелов), подпись base64, идентификация по `signer_key_id`.
- Публичные ключи: `attestations/keys/<key_id>.pub.json`; fail-closed — запись под ключом вне списка не верифицируется.
- Main-реестр дополнительно ограничен allowlist `OPERATOR_KEY_IDS` в `tools/registry/lib.mjs` (ARG-03, 2026-11-21): сессионный ключ, подброшенный в `keys/`, не может сам себя продвинуть в операторский trust root.
- `prev_record_hash` = SHA-256 канонической формы **полной** предыдущей записи (genesis = `null`); git добавляет append-only гарантию сверху.
- Trust-якоря: `attestations/keys/` — только действующие/исторические публичные ключи; приватные ключи **никогда** не в репозитории.

## 5. Подпись

### 5.1. Инструменты (фактические)

```bash
node tools/registry/verify-registry.mjs                    # main-цепь (exit non-zero при любом тамперинге)
node tools/registry/verify-registry.mjs --registry=agent   # агентская цепь
node tools/registry/build-index.mjs                        # пересборка INDEX (main); --registry=agent — агентская

node tools/registry/sign-record.mjs <draft.json>           # подпись на машине, где есть репо и ключ:
                                                           # назначает seq, цепляет, пишет records/NNNN-...
node tools/registry/offline-sign.mjs <draft.json> <privkey.json> \
     --seq NNNN --prev <prev_record_hash_hex>              # офлайн-зеркало: машина с ключом без репо;
                                                           # печатает запись в stdout, ничего не пишет и не передаёт
```

### 5.2. Порядок

Строгий порядок **N → N+1 → N+2** без перестановок: каждая следующая подпись цепляется к head, учитывающему предыдущую. Пропуск, перескок или «подпись задним числом» запрещены. Текущая очередь — пример: 0025 → 0026 → 0027 (finding-драфты probe-сессий), затем build-index, verify, push.

### 5.3. Чек-лист pre-sign (все пункты обязательны)

1. `git pull --ff-only`; дерево чистое.
2. `verify-registry.mjs` — обе цепи зелёные; head в записях **полный** (64 hex; урезанный `chain_head` в INDEX — известный дефект индекса, см. урок №1).
3. Draft не содержит `seq`/`prev_record_hash`/`signature`; поля `type` корректны.
4. Все пины draft пересчитаны и совпали полными хешами (артефакты, manifest, evidence).
5. Статус-пометки закрыты: ни одной открытой «правки», незаполненного поля.
6. Порядок подписи строгий; после каждой — немедленный verify.
7. Финал: `build-index.mjs` → verify → push → CI регенерирует каталог → пост в тред.

### 5.4. Ключи: ротация и отзыв

- Новая ротация = новый `key_id` + chain-linked amendment; старые записи остаются валидными под исходным ключом (прецедент: 2026-10-24 rotation, `correction` 0022; ключ `argus-lab-2026q4` сохранён в `keys/`, чтобы до-rekey артефакты продолжали верифицироваться).
- Потеря ключа: опубликовать старый публичный ключ (при необходимости из git-истории), переподписать затронутые записи с сохранением содержимого, оформить всю ротацию как `correction` с пином SHA-256 старого ключа — событие ротации само должно быть chain-signed.
- Утечка/отзыв: тем же днём; сессионный ключ агента не в allowlist по построению (ARG-03), хвост agent-цепи снимается до последней валидной записи, main-записи не трогаются.
- Внешний аудит: дополнения фиксируются в `ERRATA.md`; ничего в `records/`, `keys/`, `evidence/` при этом не меняется; head не сдвигается.

## 6. Переносимость: песочница ↔ сторонний кодер ↔ CI

### 6.1. Контракт среды

Прогон воспроизводим, если зависит только от: чекаута на записанном head, пинов пре-регистрации, состава платформы (раздел 1.2) и версий инструментов в `run.json`. Не требуется: абсолютных путей, переменных окружения кроме `PATH`, локали, часового пояса, сети в момент прогона (кроме живых SUT-проб, где сеть — часть предмета и фиксируется в run.json).

### 6.2. Тест второго клона

Артефакты переносимы, если во втором свежем клоне `verify-registry.mjs` (обе цепи) проходит и все пины пересчитываются. Это определение «прогон оформлен правильно».

### 6.3. Распределение ролей

| Действие | Песочница | Сторонний кодер | Консоль | CI/action (машина клиента) |
|---|---|---|---|---|
| Прогон, evidence | да | да | да | да |
| Черновики, пре-регистрация | да | да | да | да (через action) |
| **Подпись main** | если ключ держателя в среде; иначе передать драфт держателю | **нет** — `offline-sign.mjs` у держателя | нет | **никогда** (allowlist, ARG-03) |
| Agent self-test | да (`agent-sign.mjs`, session-ключ) | да | нет | по конфигурации action |

Подпись покрывает байты (canonical JSON): сборщик артефактов и держатель ключа могут быть в разных средах; `offline-sign.mjs` именно для машины «ключ есть, репо нет».

### 6.4. Передача между средами

Git bundle (`git bundle create lab.bundle --all`, проверка `git bundle verify`) или архив; поверх — `SHA256SUMS` с полными хешами; на приёме `sha256sum -c`. Для публикации бандлов — `argus-bundles` (сборка `ci/build-bundle.mjs`).

### 6.5. Запрещено в любой среде

Править пак после пина; локальные правки SUT перед прогоном (только пин); зависимость от окружения/локали/локального времени; готовая классификация в линзовых записях; приватные ключи и секреты в репо или логах.

## 7. Сводные чек-листы

**Pre-run.** Фроз закоммичен до прогона · пины полные (64 hex) · платформа зафиксирована (kind + состав) · SUT на пине · вопросы сторон закрыты · свежий каталог прогона.
**Post-run.** raw/ без правок · строки проходят построчный JSON-парс · `unit` совпадает с пре-регистрацией · manifest собран последним · второй клон зелёный.
**Pre-sign** — раздел 5.3.
**Push.** verify обеих цепей зелёный · INDEX пересобран инструментом · head записан в пост · draft-файлы консолидированы.
**Пост в тред.** Только после пуша · head, счётчики цепей, пины · цитаты — на языке оригинала, перевод помечен · сроки — только «в следующем цикле/фрозе».

## 8. Известные уроки → постоянные правила

1. **«Ошибочка 64».** `build-index.mjs` и summary-строка `verify-registry.mjs` усекают head до 16 hex; логика верификации корректна (сверяет полные `prev_record_hash`). Правило: полные 64 hex во всех данных и сравнениях; короткие — только в человеческих текстах. Патч индекса — после текущего пуша, отдельной правкой кода.
2. **Статус-пометки до подписи.** Открытая пометка блокирует подпись; разрешается до pre-sign.
3. **Row unit объявляется в пре-регистрации.** Вердикт-строки не несут per-attempt кортеж; нужны попытки — unit = attempt (обязательство по линзе, тред x402#4198).
4. **Линза без готовых ответов.** Pass condition — сама классификация чекером по frozen records; evidence содержит входы для пересчёта, не результат; несортируемое — `absent`.
5. **Отзыв ключа — тем же днём.** Allowlist не расширяется сессионными ключами (ARG-03); ротация — через `correction` (прецедент 0022).
6. **Цитаты — на языке оригинала.** Перевод помечается явно (инцидент 2026-11-22).
7. **Платформа не константа.** Стенд, консоль, CI — равноправные виды платформы; состав фиксируется на каждый прогон в пре-регистрации и `run.json`; смена сценариев/протокола = новая пре-регистрация.

## 9. Термины и определения

| Термин | Определение |
|---|---|
| **Запись (record)** | Подписанный элемент реестра: `seal`, `finding` или `correction` в main-цепи; `self-test` в агентской. Файл `NNNN-<slug>.<type>.json` |
| **Seal** | Запись «прогон был»: SUT на пине, сценарии на пинах, вердикты валидны, findings приложены полностью. Не означает «багов нет» |
| **Finding** | Запись о дефекте в стороннем компоненте с местом раскрытия и живым статусом; статусы меняются **амендментами**, не правками |
| **Correction** | Пост-коррекция запечатанной записи через `amends`; запечатанная запись не переписывается никогда |
| **Draft** | Черновик записи в `tools/registry/drafts/` без `seq`/цепи/подписи; подписант их назначает |
| **Фроз (freeze)** | Фиксация пре-регистрации до прогона; после — только correction/note |
| **Пре-регистрация** | Строки матрицы, unit, pass-правила, boundary и пины, зафиксированные до первого артефакта |
| **Row unit** | Единица строки матрицы: `attempt` (попытка) или `verdict` (вердикт); объявляется в пре-регистрации |
| **Линза** | Пре-registered проверка, где чекер классифицирует попытки только по frozen records (delivery retry vs second execution); несортируемое = `absent` |
| **`absent`** | Вердикт «признак не может быть установлен по записям» — честный результат, не сбой |
| **Canonical JSON** | Отсортированные ключи, без пробелов; объект подписи и хеширования |
| **`prev_record_hash`** | SHA-256 канонической формы полной предыдущей записи; genesis = `null`; всегда 64 hex |
| **Chain head** | Хеш канонической формы последней записи; в человеческих текстах допустима короткая форма |
| **Trust-якорь** | Публичный ключ в `attestations/keys/<key_id>.pub.json`; fail-closed верификация |
| **`signer_key_id`** | Идентификатор ключа подписанта; для main — из allowlist `OPERATOR_KEY_IDS` |
| **Allowlist (ARG-03)** | Жёсткий список операторских key_id в `tools/registry/lib.mjs`; сессионные ключи не могут самопродвинуться |
| **Agent-цепь** | Отдельный реестр самопроверок автономных сессий; per-session ключи; пинует `main_head_at_issuance`; не мержится с main |
| **`main_head_at_issuance`** | Пин head'а main-цепи на момент выпуска агентской записи (tamper-evident: порядок записей устойчив к подмене) |
| **Evidence pack** | Каталог `attestations/evidence/NNNN-slug/`: README, manifest.sha256, export-hashes.json, runs/ |
| **Пин (pin)** | SHA-256 (полные 64 hex) артефакта, зафиксированный в записи/draft'e; правка артефакта ломает пин |
| **Платформа прогона** | Вид среды: `sandbox-stand` / `console` / `ci-action`; состав фиксируется на каждый прогон |
| **SUT** | System Under Test — цель прогона (компонент/гейтвей/сервер на запиненном коммите/версии) |
| **Z-суффикс** | Обозначение UTC+0 в ISO-8601 («Zulu»): `2026-11-22T08:00:39Z` = 08:00:39 UTC. Не изобретение регламента — международный стандарт времени в строках |
| **ERRATA.md** | Журнал текстовых уточнений вне цепи; не меняет `records/`, `keys/`, `evidence/` и head |
| **Offline-first** | Каждый шаг проверяем без сети; сеть — только pull/push, пост в тред и живые SUT-пробы |

## 10. Мини-FAQ

**Меняем ли мы структуру репозиториев под этот документ?** Нет. Документ приведён к фактической структуре; ни один каталог не переезжает — пины, INDEX, verify и CI не затрагиваются. Кодовая правка в плане одна: полный `chain_head` в `build-index.mjs`/`verify-registry.mjs` (после текущего пуша).

**Можно ли править артефакт после пина?** Нет: новый артефакт + `correction`/note.

**Какой номер следующим?** Сквозная глобальная последовательность: N = последняя запись main + 1; `type` — в поле записи.

**Кодеру нужна переменная окружения?** Запрещено; значение — в скрипте или `run.json`.

**Прогон упал посреди сессии?** Каталог остаётся; повтор — новый каталог; канонический фиксируется записью.

**Структура не совпадает с разделом 1?** Исторические пути не переименовывать; отличие — новой версией RUNBOOK.
