## Результат одним абзацем

Стек ложится на QDay Aevum testnet по всей x402-линии, которую можно проверить
без средств: RPC жив (Chain ID 44005 подтверждён из нашей среды), tUSD8 —

(`/verify` → 200), а локальное рукопожатие 402 → подпись → серверная верификация
проходит целиком с защитой от overcharge/подмены получателя. Разрыв ровно один —
funding: все три канала крана требуют присутствия человека (Turnstile / email-код
/ Discord). Гибридных подписей (ECDSA + ML-DSA-65) в тестнете нет — только
roadmap-заявление. К сабмиту на Aevum Builder Challenge готовы после ручного
фонтинга; сборка демо ≈ 2 рабочих дня.

## 2. tUSD8

- Адрес: **`0x456569838f1d43009A91ebA4263147Afd7233483`**, 6 decimals —
  подтверждено тремя независимыми источниками и из нашей среды on-chain:
  `name()` → `tUSD8`, `symbol()` → `tUSD8`, `decimals()` → 6 (59–139 ms).
- Стандарт: USDC-style **FiatTokenV2** — ERC-20 + EIP-2612 permit + **EIP-3009**
  (`transferWithAuthorization` перегрузка с кортежем подписи, селектор
  `0x94718853`; `authorizationState` — `0xb7b4f61f`); EIP-712 домен
  `{name: "tUSD8", version: "2"}` (+chainId 44005 + verifyingContract).
- Прокси апгрейдимый (AdminUpgradeabilityProxy); исходник в эксплорере
  **не верифицирован** — официально: «verifier isn't working yet» в starter kit,
  `forge verify-contract` падает.
- На нашем браннер-кошельке баланс 0 (funding не прошёл, см. грабли).

## 3. x402-механика (версия и transfer-механизм)

- **Версия схемы: x402 v2**, сеть `eip155:44005`. Живой ответ фасилитатора
  `GET https://signet.qday.info/supported`:
  `kinds = [ {scheme:"exact"}, {scheme:"qday:erc4337", extra:{EntryPoint 0xC6bd…366, paymaster 0x912d…036, policy 0xB34B…1dB, accountKind kernel-v3.1, gas-лимиты userOp}} ]`,
  `signers: eip155:* → 0xC2147AFC03AD7E92E4eA1f05e64f49bCad77D532`.
- **exact = EIP-3009** (не approve+transferFrom; paymaster существует, но только
  внутри ERC-4337-схемы qday:erc4337 для smart-аккаунтов ZeroDev Kernel v3.1).
- Фасилитатор **самохостед QDay** (платформа Signet, hostname
  `signet.qday.info`), не x402.org и не CDP; `/verify` и `/settle` — POST-only,
  есть `/failure-receipt` и prepaid-кредит (`/credit/hold`, `/credit/settle`)
  по типам из их SDK `@qday/sdk` 0.6.0 (npm).
- Пейлоад-контракт v2 (из типов SDK `types/x402.d.ts`): requirements несут
  **`amount`** (не v1-шный `maxAmountRequired`) + `maxTimeoutSeconds`; payload
  несёт **`accepted`** (копия выбранных requirements) и `resource` как объект.
  Это не «их выдумка», а спека coinbase/x402 v2 — но именно на ней спотыкается
  v1-клиент (см. находку 4).

## 4. Локальный x402-прогон (шаг 3 ТЗ) — что именно выполнилось

Скрипты: `sut-qday-aevum-probe/x402_qday_handshake.py` (сервер+клиент, stdlib +
eth-account 0.14.0), evidence: `attestations/evidence/0025-qday-x402-probe/x402_handshake_evidence.json` (копия в
реестре, запись #0025).

| Шаг | Результат | Время |
|---|---|---|
| GET без оплаты | **402** + `PAYMENT-REQUIRED` (base64, v2-формат), `accepts[0].network = eip155:44005`, asset tUSD8, amount 10000 atomic = 0.01 tUSD8 | — |
| Подпись клиента | EIP-712 `Authorization(from,to,value,validAfter,validBefore,nonce)` доменом tUSD8 v2; ключ браннер-кошелька **0x60f7593386228C0f90012796DCC5c1eA5A9D436A** (подпись средств не требует) | 6.6 ms |
| Серверная верификация | recover подписи = заявленный `from`; to==payTo; value==price; окно валидно; nonce свежий → **200 + `PAYMENT-RESPONSE`** (settle помечен pending-funding) | 5.7 ms |
| Негатив: overcharge ×100 | **отклонён** (`value_matches_price=false`) — серверная привязка к цене блокирует вектор из нашего же реестра #0000 («reference client подписывает любую сумму 402») | 12.5 ms |
| Негатив: получатель = сам плательщик | **отклонён** (`to_is_payTo=false`) | 12.2 ms |

`PAYTO 0x7fA9C98a1b0C79Bdbd31c4998E9Fd0d5DCB1c9F4` — синтетический получатель
демо-ресурса (не кошелёк прогона); в боевой сборке туда идёт адрес мерчанта.

## 5. Проверка фасилитатора QDay (шаг 3-4 ТЗ)

- POST 1 (плоский v1-стиль пейлоад): **400 `{"isValid":false,"invalidReason":"invalid_format"}`** — 138.8 ms.
- POST 2 (спека x402 v2: `{x402Version, paymentPayload, paymentRequirements}`):
  **200 `{"isValid":false,"invalidReason":"merchant_not_alive"}`** — 127.9 ms.

Читаем так: формат пейлоада и подпись фасилитатор принял (ошибки формата/
подписи ушли), следующий гейт — **живость/регистрация мерчант-URL** (мой
ресурс `http://127.0.0.1:8402/resource` им не виден). `/settle` не вызывали ни
разу — это единственный шаг, который двигает деньги. Итог: **их payload не
ломает нашу схему доказательств** — наоборот, обе стороны сходятся на v2-контракте.

## 7. Гибридные подписи ECDSA + ML-DSA-65 (шаг 5 ТЗ)

- **Заявлено**: «classical ECDSA today, hybrid ECDSA + ML-DSA-65 in progress on
  Aevum Testnet; native PQ signing on 2027 roadmap» (qday.io/news, 2026-10-30).
- **Реально в тестнете сейчас: ничего из PQC.** Wiki: PQ-прекомпайлы — «Phase 2,
  not available on Aevum testnet yet», адреса-заглушки `address(0)`; спеки уже
  опубликованы (ML-DSA-65: publicKey 1952 B, signature 3309 B; hybrid = валидны
  обе подписи). Аккаунты — стандартный ECDSA. RPC-методов/tx-типов с PQC нет.
- Оффчейн-инструменты есть: `qday-io/qday-pqc-sdk` (Go, liboqs, FIPS 204).
- Для Argus: наша схема (SHA-256 хеш-цепочка + Ed25519 реестра) от PQC-статуса
  QDay не зависит; при появлении Phase 2 можно добавить ML-DSA-65-подпись как
  дополнительное evidence-поле.

## 9. Грабли

1. **Faucet непрогружаем автоматикой** — Turnstile (газ), email+код (tUSD8),
   Discord (хакатонский кран). Это главный блокер он-чейн-сettle в прогоне.
2. **RPC-фильтр по User-Agent**: дефолтный UA python-urllib ловит 403 — интеграционные
   скрипты должны шлить «браузерный»/curl UA.
3. **WS RPC не существует**, вопреки wiki — только HTTPS-поллинг.
4. **Верификация контрактов в эксплорере сломана** (официально) — критерий судейства
   «verifiable source» придётся закрывать ссылкой на starter-kit-контракты или ждать чин.
5. **v1-клиенты спотыкаются на v2-формате** (`maxAmountRequired` vs `amount`,
   `accepted`, `resource`-объект) — первый POST дал `invalid_format`.
6. qday.io (основной сайт) из песочницы недоступен (TLS timeout) — факты с него
   взяты из поисковых сниппетов; wiki `community.qday.io` и GitHub доступны.
7. `merchant-api.qday.info` из песочницы не резолвится; Merchant Portal/ключи
   (`qday_test_…`) не проверены.
8. Ошибки «не удается подтвердить tUSD8-минт» — механика выпуска токена не
   документирована (только распределение через краны).

## 10. Вердикт: готовы ли мы к сабмиту и сколько займёт сборка демо

**Готовы технически, с одним ручным шагом.** Совместимость подтверждена до
funding-шага: формат, подпись, серверная верификация, защита от overcharge —
всё зелёное; фасилитатор принимает наш пейлоад;proof-запись прогона уже в реестре
(#0025, см. ниже).

Сборка демо для сабмита — **≈2 рабочих дня**:
- полдня: ручной funding (человек: Turnstile + email + Discord), проверка баланса;
- полдня: сервер-мерчант на их стеке — их `@qday/sdk` Express-middleware
  (`requirePayment`) либо наш bare-вариант (готов, `sut-qday-aevum-probe/x402_qday_handshake.py`),
  развёрнутый на публичный URL (нужен, чтобы фасилитатор видел мерчанта);
- полдня: клиент-часть + Argus-связка (proof-запись каждого платежа по образцу
  #0025: 402-челлендж → подпись → settle → tx-хеш → хеш-цепочка);
- полдня: видео + README + чистка репо.
Риски: сломанная верификация контрактов (критерий судейства), недокументированный
SLA крана, qday.io-дашборды, не резолвящиеся из нашей сети.
